# The docs contract

Every project keeps its docs in a `docs/` folder in git. Spriggs writes to it, and the Portolan hub will read from it. This page is the format both sides agree on.

## Layout

| Path | What it is | Who writes it |
| --- | --- | --- |
| `docs/portolan.yml` | Project metadata. Only `name` is required. | People; the survey adds it if missing |
| `docs/overview.md` | What the project does, who owns it, how to call it. About 300 words. `README.md` is accepted in its place. | People and Spriggs |
| `docs/setup.md` | How to get a working copy running. | People and Spriggs |
| `docs/changes/` | One file per change (one per pull request). | Spriggs only |
| `docs/api/` | Specs generated by the build. | The build only; never edited by hand or by Spriggs |
| any other folder | Guides, decisions, runbooks, reference. | People and Spriggs |

Folders go at most two levels deep under `docs/`. For example `docs/guides/deploy.md` and `docs/guides/cloud/aws.md` are fine, `docs/a/b/c/page.md` is not.

Spriggs's `write_doc`, `edit_doc`, `move_doc` and `delete_doc` tools share one set of path rules. They only touch `.md`, `.yml` and `.html` files, never under `docs/api/` or `docs/changes/`, and never a symlink out of `docs/`. The required pages `docs/overview.md`, `docs/setup.md` and `docs/portolan.yml` can be edited in place, but never moved or deleted. `write_doc` creates a page or replaces a whole one. `edit_doc` replaces one passage of a page that already exists, and refuses a passage that is not there or that occurs more than once; it is the tool the [check pass](../spriggs/agent-harness.md#the-check-pass) corrects a claim with.

## Page frontmatter

Every markdown page under `docs/` (except change entries) starts with YAML frontmatter between `---` lines:

```yaml
---
summary: One or two sentences for a person.
audience: agent
covers:
  - packages/spriggs/src/gate/
  - action.yml
---
```

- `summary` (required): a non-empty string.
- `audience` (optional): only the value `agent`, for detail-grade pages. Any other value is an error.
- `covers` (optional): a list of code paths the page rests on. Anything other than a list of strings is an error.

Do not put dates, authors or commits in frontmatter.

### How covers is used

Before a pull request run, Spriggs lists every tracked file under `docs/` except change entries. A page is marked as affected when one of its `covers` paths matches a changed file. A match is either the same path or a folder prefix of it. A trailing `/` or `/*` (or `/**`) on a cover is ignored, so `src/gate`, `src/gate/` and `src/gate/**` all match `src/gate/decide.ts`. The model gets the affected pages as a starting point. After the run, the same matches pick the pages the [check pass](../spriggs/agent-harness.md#the-check-pass) reads back against the code, the closest match first, so a page that rests on the changed code is checked even when the run did not touch it. No model call is made to decide this.

## Links

Links between pages must work. When a heading is renamed or renumbered, or a page is moved or renamed, every link to the old anchor or path is found and fixed.

A relative link in a page under `docs/` must point to a file that exists and, when it points at a markdown page, to a heading on that page. The anchors are the ones GitHub gives a page: one per heading, lower case, punctuation removed, spaces turned into hyphens, with `-1`, `-2` and so on when a heading repeats, plus any `<a id>` or `<a name>`. Change entries, fenced code, inline code, HTML comments and links with a scheme (`http:`, `mailto:`) are skipped. A relative link that leaves the repository is reported.

This is a check on the model, not on you. It runs when the model calls `finish`. A pull request run checks only links from or to a page that run wrote, so a dead link people left elsewhere in the repository does not get in the model's way. `spriggs survey` checks every link under `docs/`, change entries and `docs/api/` aside, because the whole doc set is its job. A page the model moved or deleted counts as written, so a link to its old path is caught. The first `finish` with a dead link is refused with the list of them; a second `finish` is accepted as it is. See [Hard checks](../spriggs/agent-harness.md#hard-checks).

## portolan.yml

```yaml
name: Portolan
repo: https://github.com/bernardcosta/portolan
owner: bernardcosta
```

Known keys:

| Key | Type | Notes |
| --- | --- | --- |
| `name` | string | Required, not empty. Spriggs puts it in the survey message. |
| `repo` | string | Optional. Must be a string when set. |
| `owner` | string | Optional. Must be a string when set. |
| `issues.pattern` | regular expression | Optional. How Spriggs finds linked issue IDs in the title and description. Default `#\d+`. Must be a valid regular expression. |
| `issues.url` | string | Optional. |
| `chat.url` | string | Optional. |
| `specs` | list of strings | Optional. |

Unknown keys are kept as they are, so people can add their own fields. Spriggs checks the file whenever it writes it, and at the start of every run, where a problem is only a warning on the console. It reports a file that does not parse, a file that is not a mapping, a missing or empty `name`, a `repo` or `owner` that is not a string, and an `issues.pattern` that is not a valid regular expression.

Of the keys above, Spriggs reads two today: `name` and `issues.pattern`. The others are kept as they are and read by nothing yet. If the model writes a file that fails one of the checks, the write is refused.

## Change entries

Spriggs writes one entry per pull request under `docs/changes/`. On a later run for the same pull request it rewrites the existing entry (it finds it by the `pr` field) instead of adding a new one.

A person or a coding agent can also write the entry before the pull request exists. That entry has no `pr`. When the pull request's docs are current, Spriggs keeps the entry as it is (see [Docs already current](../spriggs/pull-request-run.md#docs-already-current)). When Spriggs makes a full run, and no entry has this pull request's number, it rewrites an entry without `pr` that the pull request added, and sets `pr`. An older entry without `pr` is never taken.

File name: `YYYY-MM-DD-<slug>.md`. The slug is the title in lower case, accents removed, words joined by hyphens and cut at a word boundary near 50 characters. A cut slug does not end in a small word such as "the", "of" or "and". If that name is taken, `-<pr number>` is added.

Frontmatter, in this order:

| Field | Rule |
| --- | --- |
| `title` | Required, not empty. |
| `kind` | One of `added`, `changed`, `fixed`, `removed`, `deprecated`, `internal`. |
| `breaking` | `true`, or left out. |
| `pr` | The pull request number. Left out when the entry was written before the pull request. |
| `coverage` | `full` or `partial`. |
| `reason` | Only when coverage is `partial`: `reason-missing` or `diff-too-large`. |
| `docs` | A list of the doc paths the change touched. |

The body is two or three sentences on what changed, why, and what a reader must do. A breaking change adds a short "What to do" paragraph.

How the fields are filled:

- `kind` comes from the Conventional Commits type when there is one (`feat` gives `added`, `fix` gives `fixed`, `perf` gives `changed`, and `refactor`, `chore`, `ci`, `build`, `test`, `style`, `docs` give `internal`). The model may narrow `added` to `changed`. With no type, the model chooses; `unknown` becomes `changed`.
- `breaking` is set when a title or commit subject has `!` after its type, or a line in the description or a commit body starts with `BREAKING CHANGE:` (or `BREAKING-CHANGE:`).
- `docs` lists the paths the model named that the run wrote or that already exist under `docs/`, plus every markdown page the run wrote. A page the [check pass](../spriggs/agent-harness.md#the-check-pass) corrected counts as written, so it joins the list even when the model did not name it. A page the run deleted is left out.
- An `internal` change gets no entry, unless the model marks it as a large refactor.
- In `--local` mode the entry is printed, not written.

## What the post-run check refuses

After the model finishes, Spriggs checks every file it changed, including the pages it deleted and any page the [check pass](../spriggs/agent-harness.md#the-check-pass) corrected. A file written back with its original content does not count, and a deleted file does count. The check fails when:

- a changed file is outside `docs/`, or under `docs/api/` or `docs/changes/`;
- a markdown page has missing or invalid frontmatter;
- `docs/portolan.yml` fails one of the checks above;
- the docs edits add up to more than 1,500 changed lines (pull request runs only; `spriggs survey` has no cap). A deletion adds no lines, and a page moved without other changes adds none either, so moving a long page does not fail the cap;
- in CI, on a pull request run, any other file in the working tree changed.

On a pull request run, a failed check fails the run and every write, move and deletion is undone. On `spriggs survey`, the files are left in place for you to review, and the survey exits with code 1.
